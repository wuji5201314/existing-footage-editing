# Existing Footage Editing

## Purpose
Turn an existing long video (interview, podcast, livestream, lecture, vlog) into publishable short clips. The quality gap is not the cutting tool — it is segment selection and the publishing workflow: clips chosen by transcript and semantic completeness, scored before they are cut, exported as a version matrix, with BGM and release copy prepared as one kit.

Distilled from the 孙宇晨访谈切片 project (2026-10): a 52-minute interview → 7 quote clips + 3 theory segments → daily Douyin releases with per-day copy packages.
Enhanced 2026-10-21 with the best ideas from kindred open-source skills (see `references/techniques.md` §13 for what was taken from each, and what was deliberately rejected):
- **cutlist** (itsryanlenk) — plan-first workflow, candidate scoring, caption/video sync check, thumbnail trifecta
- **video-agent-skills** (Melvynx) — `/clips` content inventory and cold open, `/publish` cover selection and published log
- **video-use** (browser-use) — word-boundary cuts, 30ms audio fades at cuts, self-evaluation at every cut boundary, project memory file
- **ai-video-editing-skill** (znyupup, 中文 vlog) — three-dimensional analysis (hear / see / measure), speech-truncation validation with auto-fix, Whisper hallucination filtering
- **shorts-cutter** (eliftforlife) — pause compression, end-on-payoff rule
- **jianying-editor-skill** (luoluoluo22) — acceptance checklist, low-res proxy for analysis, editor-marker handoff

## Workflow
1. **Probe before promising anything.** Resolution, fps, audio tracks, duration. State the clarity ceiling honestly: a 576p source cannot become true 720p — never upscale and pretend. Check whether subtitles are already burned in; if they are, never burn a second set. For very long sources, make a low-res proxy (360p) for frame analysis and review; always cut from the original. If the user supplied separate caption files, run a sync check first: if captions and video do not line up (different exports), stop and say what to re-export — never guess an offset.
2. **Transcribe once, with timestamps — then clean the transcript.** faster-whisper (accuracy first — the user prefers a slower, accurate model over a fast sloppy one). The timestamped transcript is the single source of truth for selection, cutting, subtitles and copy. Filter Whisper hallucinations: segments over pure music / ambient sound with mean volume below ≈ −40dB are suspect — verify against the audio before trusting their text. Recipes: `references/techniques.md`.
3. **Inventory the content before picking clips.** Read the whole transcript end to end, and tally every usable piece by kind: **Claim** (a clear position, ideally contrarian) / **Story** (a moment with a turn) / **Number** (a result, before-and-after, price, time) / **Mistake** (what went wrong + the lesson) / **How-to** (a move the viewer can apply) / **Answer** (an audience question, answered). Report the counts first ("4 claims, 2 stories, 6 numbers…"). Fewer than 4 usable pieces total: the source is too thin — say so and propose the 1–2 clips it can honestly give. Then cross-check with an **audio-energy pass** (loud runs = laughs, emphasis): energy peaks are leads to verify against the transcript, never candidates by themselves — a loud run with nothing said under it is not a clip. Any markers the user dropped while watching ("this part was good") are leads to check, not decisions.
4. **Select by semantic completeness, then score.** A clip must contain subject + premise + conclusion so it stands alone. Quote clips run 12–15s minimum; if the setup sentence is what makes the quote land, the setup is in the clip. (User correction, 2026-10-17: the first cut shipped 6–11s punchlines missing their premises and had to be fully re-cut.) Score each candidate 0–2 on six tests — **self-contained / hook in 2s / one idea / payoff ending / energy / speaker value** — and keep only ≥8/12 (recipes in techniques §9). Automatic rejects: starts on "so / and / like I said / this" with nothing introduced, leans on the long video ("as I said earlier", "in this video", "the next part"), inside jokes, crosstalk, dead air >1.5s inside the clip, a promise of results the speaker never made. Spoken numbers are the speaker's claims — quote them as such in copy, never restate them as verified facts. Ideas too spread out to clip (a point made in 3 places, a story told slowly) do not get forced into a clip: note them as "re-record / commentary" candidates instead.
5. **Write the plan before cutting anything.** One plan file per source (template in techniques §10): every clip with slug, exact start→end, length, hook line (the exact words from the transcript — no timestamp, no clip), score, why it stands alone, and its publishing kit draft. Pick the **cold open** now: the strongest complete sentence in the whole source, ≤10s — it anchors the cover and the title (step 9). Publish order: strongest first, then alternate topics so two similar clips are not back to back. Show the plan; cutting waits for the user's yes when the selection itself is new.
6. **Cut frame-accurately, word-snapped, and validate the speech boundaries.** Re-encode at delivery resolution with an accurate cut (ffmpeg-skill `cut.py --accurate --crf 18`), keeping ~0.5s of margin on each side in the rough cut, then snap to word boundaries: land each cut at the quietest point nearest the boundary so no syllable is clipped. Then run **speech-truncation validation**: no speech segment may start before the clip start or end after the clip end (0.3s tolerance); auto-fix by extending to the word edge (start → speech start −0.1s, end → speech end +0.2s) and **re-validate until clean** — do not eyeball this step. Add **30ms audio fades at every cut** so joins never pop. Optionally tighten talking-head dead air: pauses >0.6s shrink to ≈0.3s — but preserve laughs and deliberate beats. A clip must **end on a payoff** (punchline, answer, instruction), never on a trailing "so yeah…". Self-evaluate the rendered output at every cut boundary (first and last second, head and tail) before showing the user anything.
7. **Export the version matrix.** GIF loop (silent, for chat/messaging), small MP4 with sound (easy forwarding), full-source-resolution MP4 (platform upload — the file the user actually posts). Always keep clean masters untouched beside processed versions. When reframing horizontal → vertical, crop around the speaker and note the speaker focus per clip; a center crop on a two-person interview can lose one of them — say so before editing, and prefer keeping the source ratio when the platform allows it. If the user wants to fine-edit in their own editor (e.g. 剪映), also export a markers/plan file they can cut from — the plan is the handoff, not just the MP4s.
8. **Premix BGM into the file when the platform can't be trusted to layer it.** Some platform editors truncate clips when BGM is stacked in-app (Douyin multi-select + BGM squeezed clips to ~6s). Premix instead, and upload with original-sound only. Only ever use audio the user provided — never scrape, reuse, or recommend library/cloud BGM. Verify the recording's waveform in sections first (user recordings can start with long silent stretches); pick a stable section; voice 100% / BGM ≈15%; `amix normalize=0` + `alimiter` so the music never ducks or clips the voice; verify levels against the clean version before delivering.
9. **Ship a publishing kit, not loose files — with the trifecta checked.** Per clip: the file itself + title (the quote itself, copy-ready) + 3–4 hashtags + a pinned comment that asks an opinion question + cover. **Trifecta rule:** the cover text, the title, and the first line of the description must all make the *same promise* as the clip's first seconds (its cold open) — if they do not match, the viewer clicks one promise and gets another; fix the weakest of the three. **Cover selection:** never blindly take frame 0 (often a blink or a blank). Pull a contact sheet of the first ~3 seconds, pick the frame where the speaker's eyes are open, the face is expressive, and the subject sits on a left/right third leaving room for the big-text quote on the other side; then run the **legibility test** — shrink the cover to feed size (≈320px wide): if the words cannot be read, cut words, do not shrink the font. Keep a plan file with the schedule (default: one clip per day, evening window) and update it with actual progress — plans slip, the file must say so.
10. **Deliver files in chat, confirm they rendered, and log the publish.** Chat attachments occasionally fail to display; after posting a file, ask whether it showed, and re-post if it didn't. A file library is a backup, never the primary delivery. When the user confirms a clip is posted, record it in a **published log** (clip, platform, date/time, link if any) next to the plan — check this log before re-sending or re-scheduling a clip, so nothing is posted twice or chased after it is already out. Keep a short project memory file (source, decisions, quirks discovered) so the next session picks up where this one left off.

## Output Contract
- Every clip passes the semantic-completeness check (subject + premise + conclusion), the scoring threshold, and the speech-truncation validation (run twice, clean).
- The plan file exists before cutting, with hook lines quoted exactly from the transcript.
- The version matrix exists (GIF / small MP4 / full-res MP4) with clean masters preserved.
- Each clip ships with its publishing kit: title, hashtags, pinned comment, cover (trifecta-checked, legibility-tested), scheduled slot.
- The published log is updated when the user confirms a post.
- Stated limits are honest: source resolution ceiling, no re-burned subtitles, BGM only from user-provided audio.
- Acceptance checklist before declaring a batch done: files exist at the stated paths, durations match the plan, audio decodes clean, covers exist, plan and log agree.

## Operating Rules
1. Transcript first: no selection or cutting before the timestamped transcript exists.
2. Semantic completeness beats brevity — never re-cut below the standard to make a clip shorter.
3. Pairs with `ffmpeg-skill` (execution: cut, mix, loudness, export) — this skill owns selection, workflow and publishing; it owns the commands.
4. Not for generated motion video — that is `code-motion-video` + Remotion. This skill is only for footage that already exists.
5. BGM: user-provided audio only, premixed at ≈15% under full voice, levels verified against the clean master. Library/cloud music features in other tools do not override this.
6. No auto-publishing: tools that post or schedule to platforms on the user's accounts are not adopted here. The user posts manually in the app; this skill prepares everything up to that tap.
7. When a platform quirk is discovered in real use (e.g. in-app BGM truncating clips), the user's field result overrides generic advice — record it here.
8. Working scripts and intermediates live in the project folder, never inside this skill directory — the skill stays a clean, portable playbook.
